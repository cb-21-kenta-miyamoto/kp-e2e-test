# テスト観点・ケースの書式

置き場所は kpiee-designs の `docs/feature/<領域>/<改修ID>/test/`。

> **既存の正本と食い違う点がある。** kpiee-designs には
> [`docs/onboarding/test-case-format.md`](https://github.com/f-scratch/kpiee-designs/blob/main/docs/onboarding/test-case-format.md)
> があり、そこは「実施ケース行（TC001 のような展開済みケース）は作らない。観点とパターンで止める」
> と定めている。本書式は**展開済みケースまで書く**。AI に実施させるには観点とパターンだけでは
> 掛け合わせの解決・具体値・前提データが実行者の暗黙知になるため。
> **フォーマットを変えるなら正本の改訂とセットで判断する。** → dx-kpiee#18521 の未決事項

## ファイル構成

```
test/
├── index.md              目的と目次。4 レイヤーの定義、ブロック一覧、ケース群までの目次
├── overview.md           改修情報 / テスト対象範囲 / 対象外 / 基本方針 / 環境
├── test_data.md          ケースの「前提」が参照するレポート・ユーザー・権限・初期データ
├── SPEC-*.md             仕様書から読み取れる機能テストケース
├── NFR-*.md              仕様書から読み取れる非機能要件のテストケース
├── SCN-*.md              実際の業務を想定したシナリオケース
└── MB-*.md               設計書・実装から読み取れるミドルバックテストケース
```

## 4 つのレイヤー

**同じ機能でも「何を根拠にケースを起こしたか」で分かれる。落ちたときの意味が違う。**

| 接頭辞 | 何の略か | 根拠 | 落ちたときの意味 | 主な担保 |
| --- | --- | --- | --- | --- |
| `SPEC` | Specification | Notion 仕様書 / 基本設計 §3 / Figma | 仕様どおりに動いていない | 手動E2E / 自動E2E |
| `NFR` | Non-Functional Requirement | 基本設計が明示したリスク + kpiee 標準 | 使えるが運用に耐えない | API / 手動E2E |
| `SCN` | Scenario | 基本設計 §2「開発の目的」 | 個々は動くが業務にならない | 手動E2E |
| `MB` | Middle-Back | 基本設計 §4 / API 設計 / 実装 | 画面からは見えないところが壊れている | API / 単体 |

**上から下へ「仕様の言葉」→「実装の言葉」に降りる。**

### 切り分けの原則

- **`SPEC` と `MB` が重複したら `SPEC` を残す。** 画面から確認できるものは `SPEC`。
  `MB` は「画面からは確認できないが壊れうる」ものだけ
- **`SCN` は網羅を担わない。** 網羅は `SPEC` / `NFR` / `MB` の責務。
  `SCN` は「その並びで通ったときに初めて壊れるもの」を拾う
- **`NFR` の観点を内部確認にしない。** DB / Snowflake の状態ではなく、
  画面表示・応答・運用者が判断できる状態に翻訳する

## ID

- ブロック: `<接頭辞>-<連番>`（`SPEC-1`）
- ケース: ブロック内で `<グループ>-<連番>`（`A-1`）
- 文書をまたいで指すときは `SPEC-1 A-1`
- **一度振った ID は欠番にしても再利用しない**（実施記録・NG 起票から参照されるため）

## ブロック 1 ファイルの構成

```
# 【<ブロックID>】<ブロック名>
（親 / レイヤー / 前提となる文書 / ケース数の表）

## 1. 対象範囲          対象 と 対象外（対象外は他ブロックへリンク）
## 2. 観点サマリー       確認観点詳細 / パターン観点詳細（組み合わせ前の全量）
## 3. ケース一覧         ケース群とケースIDを件数つきで（手順を読まずに漏れを判断できる）
## 4. ケース             1 ケースずつ。パターン詳細 / 操作 / 期待値
## 5. 被覆表             どのパターンが 1 ケースも使われていないか
```

**順番に意味がある。** 観点があってケースが決まるので、観点サマリーがケース一覧より先。

## 1 ケースの中身

````markdown
#### A-1 本文セルにテキストのみのコメントを投稿する

##### パターン詳細
- 画面: レポート詳細
- 導線: セルの右クリックメニュー
- セル種別: 本文セル
- 操作者の権限: 編集可

##### 操作
1. レポート「E2E-全社実績」の詳細画面を開く
2. 縦軸「首都圏第一営業部」× 横軸「2026/04」のセルを右クリックする
3. 「セルにコメント」を選ぶ
4. 「前月比で伸びすぎに見えます」と入力して送信する

##### 期待値
- レポート詳細画面 の 対象セルの右上 が **未解決の印が表示された状態** になっていること
- スレッドの吹き出し の タイムライン が **自分の発言1件** になっていること
````

| 項目 | 決めごと |
| --- | --- |
| 見出し | **ケースID + 一行タイトル。** タイトルは「何をするケースか」を動詞で |
| `パターン詳細` | **`パターン観点名: パターン` の箇条書き。** キーは観点サマリーの `パターン観点名` と**文字列一致**させる。該当しない観点は `-` と書いて省略しない |
| `操作` | **番号付きの手順。実際の値まで書く。**「パターンに記載の条件で操作する」では AI が動けない |
| `期待値` | **`<確認する画面> の <確認する対象> が <確認する内容> になっていること`** の形を必ず守る |

**`期待値` の 3 分割が一番の要点。**「正しく表示されること」ではどこを見ればいいか分からず、
AI が判定できない。

## テストデータ一覧には「前準備の区分」を書く

**「何が要るか」の一覧だけでは実施できない。** `どう作るか` と `いつ作るか` が要る。

```md
## 0. 前準備

| 区分 | 誰が / いつ | 位置づけ |
| --- | --- | --- |
| A. 事前・手動 | 人が初回 1 回だけ | 画面の外に出るため spec から作れない |
| B. 事前・自動 | セットアップ spec がブロック単位で | 作れるが導線に置くと干渉する |
| C. 導線中 | ケースの手順の中で | 作成の導線そのものが確認対象 |

### A. 事前・手動 — 画面の外に出るもの

| 対象 | なぜ手動なのか | 作ったあと |
| --- | --- | --- |
| ... | ... | ... |
```

- **区分 A には「なぜ手動なのか」を書く。** 理由が無いと次の人が導線に戻して詰まる
- **成果物だけ書いて土台を飛ばさない。** 「レポート」を書いたら、その数値の元になる
  データファイルとマスタも書く。**依存を列に持たせて作る順序を出す**
- 既存 helper で自動化済みか、実装が要るかを区別して書く
- **観点表には「何が要るか」を書く。「実際に何を作ったか」は実施記録ブック側に書く。**
  環境・ワークスペース・作った名称は改修や実施回ごとに変わるので、観点表に固定しない

詳しくは [e2e-prepare の 準5](../skills/e2e-prepare/SKILL.md)。

## AI が実施できるための必須条件

| # | 条件 | 具体 |
| --- | --- | --- |
| 1 | 期待値に「どこを見るか」がある | 上の 3 分割 |
| 2 | 操作に具体値がある | レポート名・階層名・入力文字列まで |
| 3 | 前提の作り方がある | `test_data.md` に実体を並べ、ケースの `前提` から ID で参照する |
| 4 | 1 ケース 1 目的 | 期待値が 3 つ以上に増えたらケースを割る |

## 期待値が確定しないときの印

| 印 | 意味 | どうするか |
| --- | --- | --- |
| `※実装読み` | 設計書に記述が無く、実装を読んで書いた期待値 | 実施の前に画面で確かめて確定させる |
| `※未確定` | 期待値そのものが決まっていない | 設計書へフィードバックして人間が判断する |

**この印が付いたケースはレビューで全件読む。** 読まずに承認すると
「実装に合わせたテスト」を通すことになる。
