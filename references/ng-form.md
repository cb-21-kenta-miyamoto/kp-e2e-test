# NG フォームへの投稿

組織共通の **NG 登録フォーム**へ、AI が起票した NG を投稿するための仕組み。
`e2e-ng-report` から参照する。

## なぜ中間テーブルが必要か

**AI から NG フォームへ直接投稿できない。** 試した経路と結果:

| 経路 | 結果 |
| --- | --- |
| `viewform` を HTTP で叩く | 401。ログイン必須（社内フォーム） |
| `formResponse` へ POST（Bearer トークン付き） | 401 |
| Google Forms API (`forms.googleapis.com`) | 403。**そもそも回答の作成に非対応**（読み取り専用） |
| Apps Script `FormApp.createResponse().submit()` | **通る。** ただしフォームの編集権限が必要 |

残るのは Apps Script だけ。Apps Script は**人のアカウント権限で動く**ので、
「AI が下書き → 人が承認 → 人の権限で投稿」という形に自然に落ちる。

```
AI ──(Sheets API)──▶ 【NG管理】ブックの NG一覧 に 1 行書く
                          │
                          │ 人が内容を確認して『送信』(V列) にチェック
                          ▼
                     Apps Script（人の権限で動く）──▶ NG フォーム
                                                        │
                                                        ▼
                                        【kp】NG一覧「【編集厳禁】NGフォーム」タブ
```

## フォームの ID は 2 つある。取り違えない

| | URL の形 | 用途 |
| --- | --- | --- |
| 回答用 ID | `/forms/d/e/1FAIpQLS…/viewform` | 人が回答する。誰でも開ける |
| 編集用 ID | `/forms/d/<別の文字列>/edit` | `FormApp.openById()` が要求するのはこちら |

**この 2 つは相互に変換できない。** 回答用 URL しか手元に無いとき、Drive を名前で探すのは
当てにならない（実際に別フォームを掴み、項目数 7 と 25 の食い違いで気づいた）。

**確実な導出経路は回答シートから引くこと。** 回答が流れ込むシートはフォームに紐づいているので
`Sheet.getFormUrl()` が編集用 URL を返す。`NGForm.gs` の
`findFormIdFromResponseSheet()` がこれをやる（メニュー「回答シートからフォームIDを取り出す」）。

| | |
| --- | --- |
| 回答用 | https://docs.google.com/forms/d/e/1FAIpQLSdwLHKQb4_c67mGVHrZvgwXS2B0VTJaMF7MzrJDfY7t-q-60Q/viewform |
| 編集用 | https://docs.google.com/forms/d/1_lwMxYz7d8i5yWqpplXalqm_1EHjMvwv2MSTsn7vJtI/edit |
| 回答先 | 【kp】NG一覧 の `【編集厳禁】NGフォーム` タブ（`159r0cLcqNY9w3xrp4D_ELgu5a5OV5drkfrIVRrGy39U`）|

## フォームの構造（25 項目）

**セクション区切り（`PAGE_BREAK`）が 3 つあり、デバイスの回答でページが分岐する。**
`PAGE_BREAK` は回答を持てないので、対応列は空のままにする（スクリプトも読み飛ばす）。

```
お名前 / 検知したデバイス
├─[PAGE_BREAK] PC       … アプリ種別（PC） / OS
├─[PAGE_BREAK] モバイル端末 … アプリ種別（モバイル） / OSバージョン / 端末 / 端末名 / アプリバージョン
└─[PAGE_BREAK] NG報告    … 再現デバイス / テスト種別 / バグ検知環境 / 本番環境での再現有無
                          / インシデントレベル / 開発対象ID / テストケースリンク / NG事象
                          / 再現方法 / 証跡（画像・動画）/ 事象が起きている時間
                          / フロントNGフラグ / リリースSprint（起票時）
```

- **`証跡（画像・動画）` は `TEXT`。** `FILE_UPLOAD` ではないので Drive のリンクを文字列で送れる
  （`FILE_UPLOAD` なら Apps Script から投稿する手段が無い）
- PC で起票する限り、モバイルページの必須項目は**埋めなくてよい**。
  `FormResponse.submit()` は必須チェックをしないため、未指定のまま通る
- ブラウザ経由の E2E は PC 固定なので、デバイス系 5 項目は**固定値**で埋まる

### 選択肢（実回答 1999 件から確認した実値）

2026-09-07 時点。**正本は `diagnose()`。ここは目安。**

| 項目 | 値 |
| --- | --- |
| 検知したデバイス | `PC` / `モバイル` |
| アプリ種別（PC） | `ブラウザ` のみ |
| OS | `Mac` / `Windows` |
| 再現デバイス（複数可） | `iOS` / `Android` / `PC（ブラウザ）` |
| バグ検知環境 | `IT` / `STG` / `UT` / `STG02` / `本番` |
| インシデントレベル | `Lv.3` / `Lv.2` / `Lv.1` |
| 本番環境での再現有無 | `再現する` / `再現しない` / `新規機能のため確認不要` |
| フロントNGフラグ | `フロントNGである` / `フロントNGでない` |
| リリースSprint（起票時） | `Sprint 19` / `Sprint 19.1` / `Sprint 20` / `Sprint 20.1` / `Sprint 21` / `Sprint 21.1` |
| テスト種別 | 下の表のとおり |

### テスト種別 は 4 レイヤーに対応している

`テスト種別` の選択肢は、ケースのレイヤー接頭辞とそのまま対応する。**迷わずここで決める。**

| ケースの接頭辞 | テスト種別 |
| --- | --- |
| `SPEC-*`（画面仕様）| `STG/UTテスト(フロント)` |
| `NFR-*`（非機能）| `STG/UTテスト(フロント)` |
| `SCN-*`（業務シナリオ）| `STG/UTテスト(ユーザーストーリー)` |
| `MB-*`（ミドルバック）| `STG/UTテスト(ミドルバック)` |
| ケース外で見つけたもの | `STG/UTテスト_ケース外` |

残りの選択肢は E2E では使わない:
`リグレッションテスト` / `リグレッションテスト_ケース外` / `新規エラーログの潰しこみ` /
`クラッシュの潰しこみ` / `モンキーテスト` / `仕様質問` / `調査からの起票`

> [!WARNING]
> **`ITテスト` はもう選択肢に無い。** 過去の回答に 446 件あるが、フォームは編集されている。
> 同様に `ケース内NGのため確認不要`（→ `新規機能のため確認不要`）、
> `PC（アプリ）`、`デスクトップ` も消えている。
> **`リリースSprint` は `Sprint 21`（半角スペース有り・`.0` なし）。** `Sprint21.0` は通らない。

**選択式は選択肢と完全一致しないと弾かれる。** 正本は「フォーム項目」タブの `選択肢・注意` 列
（`listFormItems` が書き出す）。上の表は目安。

> [!WARNING]
> **`バグ検知環境` に「ローカル」が無い。** ローカル実施の NG をどう分類するかは
> 運用の決めごと。既定は `UT` にしている。
> **`リリースSprint（起票時）` は `LIST` で、選択肢は Sprint 毎に増える。**
> 固定値でハードコードせず、毎回タブの選択肢列から取る。

## 【NG管理】ブックの列（25 列）

`AIテスト/` 直下・改修横断で 1 本。
1 行 = 1 件の NG。`NG_FIRST_ROW = 5`（4 行目が見出し、5 行目が記入例）。

| 列 | 見出し | フォームへ |
| --- | --- | --- |
| A | NG ID | — |
| B | 起票日 | — |
| C | 改修ID | `開発対象ID` |
| D | 機能名 | — |
| E | 発見元ケース | — （`SPEC-1 A-3` か `ケース外`）|
| F | テストケースリンク | `テストケースリンク` |
| G | NG事象 | `NG事象` |
| H | 再現方法 | `再現方法` |
| I | 期待する結果（内部） | — |
| J | 実際の結果（内部） | — |
| K | 証跡リンク | `証跡（画像・動画）` |
| L | バグ検知環境 | `バグ検知環境` |
| M | テスト種別 | `テスト種別` |
| N | インシデントレベル | `インシデントレベル` |
| O | 本番環境での再現有無 | `本番環境での再現有無` |
| P | フロントNGフラグ | `フロントNGフラグ` |
| Q | 事象が起きている時間 | `事象が起きている時間` |
| R | リリースSprint（起票時） | `リリースSprint（起票時）` |
| S | 原因・解消方針（内部） | — |
| T | 検出元PR（内部） | — |
| U | GitHub Issue（内部） | — |
| V | **送信** | ← ここにチェックすると投稿される |
| W | 送信済み日時 | スクリプトが書く |
| X | フォーム回答ID | スクリプトが書く |
| Y | 送信エラー | スクリプトが書く |

- **`（内部）` 列はフォームに送り先が無い。** ブック内だけで持つ
- `お名前` / `検知したデバイス` / `アプリ種別（PC）` / `OS` / `再現デバイス` は**固定値**
  （「フォーム項目」タブの `対応する列` に `"PC"` のように書く）
- `NG事象` はフォーム側に「期待値」「実際」の欄が無いので、
  **事象 + 期待値 + 実際を 1 つのテキストに畳んで送る**（I/J はブック内の控え）

## セットアップ（人がやる。初回だけ）

1. 拡張機能 → Apps Script に [`apps-script/NGForm.gs`](../apps-script/NGForm.gs) を貼って保存
2. ブックを開き直す（`NGフォーム` メニューが出る）
3. **NGフォーム → 回答シートからフォームIDを取り出す**
4. **NGフォーム → 準備する（初回だけ）** — 承認 → 項目読み込み → `onEdit` トリガー設置
5. 「フォーム項目」タブの `対応する列` を確認

承認画面で「このアプリは確認されていません」が出たら
詳細 →（安全ではないページ）に移動 → 許可。

`onEdit` は**インストール型トリガーでないと `FormApp` を触れない**ので、
手順 4 の `prepare` が `ensureTrigger_` でトリガーを張る。
単純な `onEdit(e)` 関数のままだと権限不足で落ちる。

## 送信できないとき

**チェックしたのに `送信済み日時`・`送信エラー` の両方が空**なら、`submitRow_` に
到達していない。この経路は NG一覧 に何も書かないので、シートを見ても分からない。

**メニュー → 送信できないとき — 状態を調べる**（`diagnose()`）を押す。
スクリプト版・列の解決結果・トリガーの有無・フォーム・マッピング・対象行を一度に出す。

| 症状 | 原因 |
| --- | --- |
| `送信済み日時` も `送信エラー` も空 | onEdit が発火していない（トリガー無し / 列を見失っている / スクリプトが古い）|
| `送信エラー` に理由が入っている | `submitRow_` までは動いた。理由を読んで直す |
| `必須なのに空: 〜` | その列が空。フォームに中途半端な回答を残さないため送信を止めている |
| `項目が見つからない: 〜` | フォーム側の項目が変わった。「フォームの項目を読み込み直す」 |

> [!WARNING]
> **列を組み替えたら、スクリプトを貼り直す必要があるかを必ず考える。**
> かつて `送信` 列を Q → V に動かしたとき、エディタ側は `COL_SEND = 17` のままで
> `onEditHandler` が対象列を見失い、**エラーも出ないまま何も起きなくなった。**
> 現在は列を**見出し名で引く**（`ngCols_`）ので同じことは起きないが、
> `SCRIPT_VERSION` を `diagnose()` で確認して、古い版が残っていないかを見る。

### 選択肢に無い値だと言われる

```
アイテムに無効な回答が送信されました: IT
```

これは `createResponse()` が投げる Google 側のメッセージ。**どの項目かも、何なら通るのかも
出ない。** スクリプト側で送る前に選択肢と突き合わせるようにしたので、いまはこう出る。

```
1 件の問題で送信を中止しました:
  ・選択肢に無い値です: 「バグ検知環境」に "IT" を送ろうとしました（L列）
      選択できるのは: "UT" / "STG" / "IT"
```

原因は 2 つに絞られる。

| | 見分け方 |
| --- | --- |
| **選択肢が変わった** | `diagnose()` の「選択式項目の選択肢」に無い |
| **見た目が同じで文字が違う** | 一覧にはある（末尾の空白 / 全角の `ＩＴ` / NBSP）|

後者は `normalizeChoice_` が吸収する（NFKC 正規化 + 空白除去 + 小文字化）ので、
**吸収したうえでフォーム側の正式表記に直して送る。** それでも落ちるなら前者。

> [!WARNING]
> **過去の回答から選択肢を推測しない。** 回答シートの過去回答は「当時の選択肢」で、
> フォームは編集されている。正本は `diagnose()` か「フォーム項目」タブの `選択肢・注意` 列。

### そもそも打てないようにする

選択式の列（`L,M,N,O,P,R`）には**フォームの選択肢そのものをドロップダウン**にしてある。
選択肢が変わったら、メニュー「フォームの項目を読み込み直す」→
**「選択肢をドロップダウンに反映する」**（`syncChoiceValidation()`）で追随させる。
`準備する（初回だけ）` はこれも一緒にやる。

**`CHECKBOX` と「その他あり」の項目だけは選択肢外の入力を許す**
（複数選択はカンマ区切りで入れるため）。

### 1 行から 2 通投稿される

**`setValue` は実行の終わりまで遅延される。** ロックを持っている間に書いても、
解放した時点では他の実行からまだ見えない。

```
実行A: ロック取得 → W を読む（空）→ 送信(4秒) → W に日時 → 解放
実行B:          ロック待ち ───────────────────→ 取得 → W を読む（★まだ空）→ 送信
```

「読む → 送る → 書く」の順だと `LockService` だけでは排他にならない。
**送る前に印を立てて `SpreadsheetApp.flush()` する**（claim-then-act）。

```js
sh.getRange(row, col.sentAt).setValue(CLAIM_MARK);  // '送信中…'
SpreadsheetApp.flush();   // これが無いと確保が他の実行に見えない
```

失敗したら印を外す。外し忘れるとその行は以後ずっと送れない。

実行が 2 つ走る原因は 2 つ。`diagnose()` の `■ トリガー` で切り分ける。

| | 見分け方 | 直し方 |
| --- | --- | --- |
| onEdit トリガーが 2 つ以上 | `■ トリガー` が 2 件以上 | `準備する（初回だけ）` が余りを削除する |
| チェック直後にメニュー送信も押した | トリガーは 1 件 | どちらか一方にする |

> [!WARNING]
> **`ensureTrigger_` は「あるか無いか」だけ見てはいけない。**
> 存在チェックだけだと 2 つあっても放置され、1 回の編集で 2 回発火する。
> 余りを `deleteTrigger` で消す。

> [!CAUTION]
> **フォームに投稿された回答は取り消せない。**
> 誤投稿はフォームの回答画面から人が削除する。組織の共有データなので AI は触らない。

### 投稿する前に検証する

**フォームに投稿された回答は取り消せない。**
メニュー「チェック済みの行を検証する（送信しない）」で先に確かめる。
必須の空・選択肢違反・型変換の失敗が `送信エラー` 列に出て、投稿はされない。

**トリガーが無くても送れる。** 「チェック済みの行をまとめて送信する」は
メニューから直接動くので、トリガーに依存しない。

## AI がやること / やらないこと

- **やる**: `NG一覧` に行を書く（Sheets API）。承認不要
- **やらない**: `V列` のチェック。**投稿の判断は人が持つ**（GitHub issue の起票と同じ承認ポイント）

**送信済みの行は再送されない。** 直すときは `W` と `X` を消してからチェックし直す。
