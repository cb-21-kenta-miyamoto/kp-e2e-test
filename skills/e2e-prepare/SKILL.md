# e2e-prepare

## 概要

実施フェーズをブロック単位で並列に回せるようにするための前準備。**1 回だけ実行する。並列にしない。**

**共有ファイルをここで確定させ、実施フェーズではブロック固有のファイルしか触らせない。**
そうしないと、並列で走るサブエージェントが同じファイルを書き換えて push が衝突する。

## いつ使うか

- `e2e-case-review` でケースが承認され、実施に入る前

## 手順

### 準1. Drive とスプレッドシートを用意する

手順は [`references/drive-and-sheets.md`](../../references/drive-and-sheets.md)。

1. `AIテスト/<改修ID> <機能名>/` と `証跡/` を作る
2. `【FMT】ケース一覧・実施記録` をコピーして改名する
3. サマリタブのリンクを埋める（設計 PR / 実装 PR / ケース PR / 実施方針 issue / 証跡フォルダ / spec PR）

### 準2. ケースを 1 行 1 ケースへ展開する

ブロック文書から機械的に抽出して「ケース一覧・実施記録」タブへ流し込む。

| 列 | どこから |
| --- | --- |
| レイヤー / ブロック | ファイル名の接頭辞 |
| ケースID / ケース名 | `#### <ID> <タイトル>` の見出し |
| 確認観点 | ケース群の `対応する確認観点` |
| 担保 | ブロックの既定（`index.md` の担保の振り分け）|
| 備考 | ケース本文に `※実装読み` / `※未確定` があれば印を付ける |

- **8 行目から流し込む**（7 行目は記入例なので消さない）
- プルダウンと条件付き書式を全行へ広げる
- **ケース定義列（A–I）は以降 AI が書き換えない**

### 準3. Spec の PR を「箱だけ」作る

**ケース本体の spec は書かない。** 共有ファイルだけを確定させる。

| 作るもの | 実施フェーズで触るか |
| --- | --- |
| `playwright.config.ts` の project 追加 / reporter 設定 | 触らない |
| `tests/<改修ID>/` ディレクトリ | — |
| `page-objects/<機能>.page.ts`（セル指定・操作の共通化）| 原則触らない。足りなければ親へ依頼 |
| `api-clients/<機能>.api.ts`（seed / 前処理）| 同上 |
| `fixtures/users.ts`（複数ユーザーの storageState）| 触らない |
| `scripts/upload-evidence.sh` | 触らない |
| **`tests/<改修ID>/<ブロックID>.spec.ts`** | **サブエージェントが書くのはここだけ** |

```ts
// playwright.config.ts
reporter: [["html"], ["json", { outputFile: "results.json" }]],
use: { video: "on", trace: "on", screenshot: "only-on-failure" },
```

**ドラフト PR で出す。**

### 準4. `※実装読み` の期待値を確定させる

**spec を書く前にやる。** 実装から読んだ期待値のまま spec にすると
「実装に合わせたテスト」になって意味がなくなる。

1 ブロック目を**実際に画面で触って**確かめる。探索用の spec を書いて
DOM とメニュー項目を吐かせるのが早い（[`references/playwright-kpiee.md`](../../references/playwright-kpiee.md)）。

確定したら**ケース側（kpiee-designs）の期待値を直し、印を外す。**
確定できなかったものは設計書へフィードバックする。

### 準5. テストデータを 3 区分に分けて用意する

**原則は「導線中に作れるものは導線で作る」。** 作成の導線を通ること自体が回帰確認になる。
そのうえで次の 2 つは先に作る。

- **対象プロダクトの画面だけでは完結しないもの** — 招待メールやスプレッドシートを開く必要がある
- **並列実施で干渉するもの** — ブロックごとに分けないと他のブロックの操作で壊れる

| 区分 | 誰が / いつ | 判断基準 |
| --- | --- | --- |
| **A. 事前・手動** | 人が初回 1 回だけ | 画面の外に出る。**spec から作れない** |
| **B. 事前・自動** | セットアップ spec がブロック単位で | 画面 / API で作れるが、導線に置くと干渉する |
| **C. 導線中** | ケースの手順の中で | 作成の導線そのものが確認対象 |

> [!IMPORTANT]
> **区分 A を最初に済ませる。ここが実施のブロッカーになる。**
> kpiee では**権限別ワークスペースユーザーが区分 A** だった。
> ユーザー作成は Cognito の招待メールを開いてパスワードを設定する必要があり、
> **spec から作れない。** これを飛ばしたため、権限が絡むケース
> （SPEC-1 `A-4` / `A-5` など）が全ブロックで止まった。
>
> 一度作れば **ユーザーごとに `storageState` を保存して使い回せる**ので、
> 前準備は初回 1 回で済む。

> [!IMPORTANT]
> **作ったものは「どの環境の、どのワークスペースに、どんな名前で」作ったかを記録する。**
> 用意したこと自体を記録しても、**実施する側が対象を特定できない。**
> 権限別ユーザーのメールアドレス、レポートの表示名、ワークスペースの ID と名称まで書く。
> ここが空だと、実施は「ブロックのため未実施」で止まる。
>
> 実施記録ブックのサマリタブの `■ 事前準備` に書く（FMT に入っている）。
> **環境は「ワークスペースの URL」を貼る。** `https://it.kpiee.xyz/dx/workspaces/149/reports` のように、
> URL 1 本で環境とワークスペースID が一意に決まる。「ローカル」「IT」だけでは特定できない。
> 環境が全行同じなら、節の先頭で既定を 1 回宣言して各行は空欄でよい。

**テストデータ一覧に「何が要るか」だけ書いて満足しない。**
`どう作るか` と `いつ作るか`（3 区分のどれか）を必ず併記する。
区分 A には**なぜ手動なのかを書く。** 理由が無いと、次の人が導線に戻して詰まる。

**土台のデータを飛ばしていないか確かめる。** kpiee では「レポート」だけが書かれ、
その数値の土台である**階層データ（マスタ）とデータファイルの記載が 0 件**だった。
成果物に近いものから書くと、その下の層が抜ける。**依存を列に持たせて作る順序を出す。**

**既存の自動化がどこまで面倒を見るかを、コードで確認する。**
「手動でやるしかない」と決める前に helper を読む。

```bash
ls <repo>/e2e-test/helpers/ && grep -n "async \|^export class" <repo>/e2e-test/helpers/*.ts
```

### 準5-b. ブロックごとの専用テストデータ（区分 B の分離）

> [!WARNING]
> **これがいちばん効く。**
> 複数のサブエージェントが同じデータを触ると互いのテストを落とす。
> **同じデータを別のエージェントが触って落ちた失敗は「プロダクトの不具合」に見える。**
> ファイルや push の衝突は git で気づけるが、これは気づけない。

- ブロックごとに専用のレポート / データファイルを用意する
- 作るのは API 経由（UI で作ると数が捌けない）
- 状態が残る機能なら**前処理で消す仕組み**も用意する

### 準6. `data-testid` の要否を判断する

対象コンポーネントに `data-testid` が無いと、ロケータが i18n の文言依存になり
文言変更で一斉に割れる。**testid 追加 PR を切るかをここで決める。**

```bash
grep -rho 'data-testid="[^"]*"' <対象ディレクトリ> | sort -u
```

## 完了の条件

- スプレッドシートに全ケースが並んでいる
- Spec の PR（箱）がマージ可能な状態
- `※実装読み` が 0 件
- ブロックごとの専用データがある

## 次にやること

[`e2e-execute`](../e2e-execute/SKILL.md) を **1 ブロックだけ**で回して、
①〜⑧ が通ることを確かめる。**いきなり全ブロックを並列で走らせない。**
