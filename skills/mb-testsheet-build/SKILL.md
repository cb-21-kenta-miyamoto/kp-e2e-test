# mb-testsheet-build

## 概要

`e2e-case-create` が作ったブロック文書（`docs/feature/<領域>/<改修ID>/test/`）を、
**PD / QA の正式様式である「改修テストシート（ミドルバック FMT）」へ展開する**スキル。

シートの構造・数式・落とし穴は [`references/mb-testsheet.md`](../../references/mb-testsheet.md) が正本。**先に読む。**
手順の正典は [dx-kpiee#18721](https://github.com/f-scratch/dx-kpiee/issues/18721)。

> [!IMPORTANT]
> **`e2e-prepare` とは対象のシートが違う。**
> `e2e-prepare` は AI 実施エージェント用の `【E2E】ケース一覧・実施記録`（4 タブ・1 行 1 ケース）。
> こちらは PD / QA が使う改修テストシート（**1 ブロック = 3 枚組**の 4 層構造）。
> **どちらを作るのか、起動時に確認する。**

## いつ使うか

- ケース PR が固まって、PD / QA へ渡すシートを起こすとき
- ディシジョンテーブルだけ先に作って、観点の掛け合わせをレビューしてもらいたいとき

## 手順

### 1. ブロック文書が前提を満たしているか確かめる

**この 2 つが揃っていないとディシジョンテーブルが作れない。** 足りなければ**先にケース PR を直す。**

#### 1-1. `対応する確認観点` がケース単位で書かれているか

```
- **対応する確認観点**: 2 の #2「一覧の並びと内容」（B-1〜B-2） / #3「紐づき先の表示」（B-3〜B-4）
```

群単位（`#2「…」/ #3「…」`）だと、**1 群が複数の観点を担保する場合にどのケースがどの観点か決まらない。**
DT は 1 列 1 観点なので、先頭の観点しか `○` を打てず残りが未担保に見える。

> [!WARNING]
> **ここは自動化しない。** ケース名と期待値の文字列一致で割り当てを試すと外れる。
> `IMP_KP001350` の `SPEC-2` G 群では 6 件すべてが #8 に寄り、#10「一覧の更新」が空になった
> （`G-2 解決すると一覧のグループが移る` は明らかに #10 側）。**人が決める。**

単一観点の群も同じ形に揃えておくと、全ケースが一意に読めて後段が単純になる。

#### 1-2. 1 軸で複数の値を使うケースの複合値が宣言されているか

ケースの `パターン詳細` には次のような書き方が出てくる。

```
- 対象 API: ①②③④⑤⑥⑦（7 本すべて）
- 確認する場所: セル上の印 / コメント一覧サイドパネル
- スレッドの状態: 解決済み → 未解決
```

DT は 1 軸 1 `○` なので、**この文字列そのものを `■パターン観点詳細` の値として宣言する。**
値はケースからそのまま取るので判断は入らない。`IMP_KP001350` では 18 ファイル / 54 件を追記した。

#### 1-3. 構造の抜けを拾う

DT を機械生成しようとして初めて出てくる。`IMP_KP001350` では 2 件あった。

- ケース群の見出し（`### D. ケース：…`）が無く、`対応する確認観点` 行が前の群の中に孤立していた
- あるブロックの全群に `対応する確認観点` 行が無かった

### 2. スコープと運用を決める（人に確認する）

| 決めること | `IMP_KP001350` での結論 |
| --- | --- |
| どのブロックを載せるか | 全 25 ブロック（MB も載せた）|
| 期待値が複数あるケース | **1 ケース = 1 行。期待値は 3 列とも改行で行を揃えて並べる** |
| `IT実施フラグ` | SPEC 全部 + `SCN-1` + `NFR-2/4/5/6/7` に `●`。`NFR-1`（性能）/ `NFR-3`（並行性）/ MB は空 |
| `期待値確認環境` | フロント系 `web / 任意 / -`、MB 系 `- / - / -` |

`FMTチェックシート` #15（実施対象外のタブに「テストケース」を含む名前を付けない）があるので、
**載せないブロックのタブは作らない。**

### 3. ブックを用意する

**参照ブックを直接書き換えない。** 複製して `テスト概要` の改修ID・リリース日・担当者・開発対象IDを差し替える。

そのあと [`references/mb-testsheet.md`](../../references/mb-testsheet.md) の
「複製直後に壊れているところ」の 3 件（`SheetURLMap` / `getSheetsWithWord()` / `■テストケースリンク`）を直す。
**ここを飛ばすとリンク列が全滅したまま進む。**

### 4. 観点サマリを埋める

ブロック文書の `## 2. 観点サマリー` をそのまま移す。

- `■確認観点詳細` → `ID / 確認観点名 / 確認観点詳細`
- `■パターン観点詳細` → `ID / パターン観点名 / パターン`（**1 行 = 1 値**）
- `ケース一覧` の `ID` はブロックID、`ケースリンク` は `テストケース_<ID>` への `HYPERLINK`

> [!WARNING]
> **ブロック文書のパターン観点詳細セクションは、見出しの直後に解説文と別の表がある。**
> 見出しでアンカーして表を拾うと解説表を混ぜる（`SPEC-1` で軸が 19 → 31 に膨らんだ）。
> **表ヘッダー行（`| # | パターン観点名 | パターン |`）でアンカーする。**

### 5. ディシジョンテーブルを作る

`ディシジョンテーブル_×××` を複製し、パターン行 / 掛け合わせ列 / 確認観点行を必要数まで広げる。

- 上段 `E`/`F` に パターン観点名 / パターン。**`E` 列は見た目が繰り返しでも全行埋める**
  （空欄があると設定マスタが引けない）
- `C` 列に `=COUNTA(UNIQUE($E$7:$E<row>))`
- 行 6 の掛け合わせ番号（`G6=1`、以降 `=前列6+1`）
- `○` は**ケースの `パターン詳細` から機械生成。1 ケース = 1 列**
- 下段 `E`/`F` に 確認観点名 / 確認すること、`D` に観点No.、ラベル行に `INDEX`+`match` の式
- 下段の `○` は **1-1 のケース単位の割り当てから**

**表記ゆれは正規化で吸う。** 括弧・空白・バッククォートを落として突き合わせ、
一意に決まるときだけ寄せる。曖昧なら**寄せずに残して人に出す。**

### 6. 4 行目にケース群のラベルを置く

**DT だけ見ても「どういう観点で組み合わせたか」が読めない。** 群ごとに 4 行目へラベルを置き、
列範囲ぶんセルを結合する（`wrapStrategy: WRAP` / 行高 104px）。

```
B. 一覧にスレッドと紐づき先が並ぶことを確認するケース（列4-7 / B-1〜B-4）
確認観点: #2「一覧の並びと内容」（B-1〜B-2） / #3「紐づき先の表示」（B-3〜B-4）
振る軸: 一覧の母集合 × スレッドの紐づき先
固定: 開く導線=トップバーの「コメント一覧」ボタン、操作者の権限=管理者
```

- **振る軸** = 群のなかで 2 値以上に振れている軸（＝組み合わせている軸）
- **固定** = 群の全列に同じ値で現れる軸（＝押さえている条件）

どちらも `○` の並びから機械的に出せる。**ケースIDは連続とは限らない**ので `A-1・A-4` の形に圧縮する。

### 7. 設定マスタ

`設定マスタ_×××` を複製し、`F3` にブロックID、行 15 に軸名を並べる。座標とケース数は自動導出。

軸数の増減は [`references/mb-testsheet.md`](../../references/mb-testsheet.md) の
「作業中に踏む落とし穴」に従う（**列を削除すると座標が消えて `#REF!`**）。

### 8. テストケース

`テストケース_×××` を複製し、`G1` にブロックIDを入れる。
`テストパターン` 列を軸数に合わせ、行 15 の結合を張り直す。

人が入れるのは次だけ（`実施目的` と `テストパターン` は数式が引く）。

| 列 | 入れるもの |
| --- | --- |
| `#` | `=ROW()-ROW($D$17)` |
| `IT実施フラグ` | 手順 2 の決定 |
| `期待値確認環境` | 手順 2 の決定 |
| `個別手順` | **1 行目に `[<ブロックID> <ケースID>] ケース名`**、その下にケースの `操作` 手順 |
| `パターンNo.` | DT の列番号 |
| `観点No.` | DT 下段の番号 |
| `確認する画面` / `確認する対象` / `確認する内容` | ケースの期待値を 3 分割（既定式を上書き）|

> [!IMPORTANT]
> **ケースIDを `個別手順` に置くのが唯一の追跡手段。**
> シートに専用列が無く、`個別手順` は GAS が見ない自由記述。
> これが無いとケース PR を直したときに対応行が分からなくなる。

**期待値の 3 分割**は `{確認する画面} の {確認する対象} が **{確認する内容}** になっていること` を割る。
`API の応答 が` のように `の` の前後に空白が無い書き方もあるので、空白なしも許すパターンを用意する。

### 9. 検算する

**ブロックごとに次を全部 0 / 一致にする。**

| 見るもの | 期待 |
| --- | --- |
| DT 下段ラベル行の `-` の数 | **0**（全列で `観点No.` が解決している）|
| 1 軸に `○` が 2 つある列 | **0** |
| 確認観点の `○` の総数 | **列数と一致** |
| テストケースの数式エラー（`#REF!` / `#N/A` 等）| **0** |
| 期待値 3 列が空の行 / テストパターンが空の行 | **0** |
| `テスト概要` の `計` | **ケース総数と一致** |

### 10. 仕上げ

- `FMTチェックシート` #9 に従い **`設定マスタ_*` と `*_×××` を非表示**にする
- タブ順をブロック順に並べ替える
- `FMTチェックシート` 21 項目を通す
- **`テストデータ一覧` を表示に戻して埋める**（複製直後は非表示。ケースの `前提` が参照する実体の置き場）

## 完了の条件

- [ ] ブロックごとに 3 枚組が揃っている
- [ ] 手順 9 の検算が全部通っている
- [ ] `観点サマリ` の `ケース一覧` から各 `テストケース_*` へリンクが飛ぶ
- [ ] `テスト概要` の `計` がケース総数と一致している
- [ ] `設定マスタ_*` と `*_×××` が非表示

## 人に出すもの

**機械的に出せて、人が判断すべきもの。** 作り終えたら必ず報告する。

| 出すもの | 意味 |
| --- | --- |
| **ケースが 1 件も無い確認観点** | ケースを足すか観点を畳むか。`IMP_KP001350` では 4 件 |
| **`○` が付かないパターン** | 取りこぼしか、ケースが書いていない暗黙の既定値か。`IMP_KP001350` では 116 件 |
| **表記ゆれで寄せたもの / 寄せられなかったもの** | ケース PR の誤字が混ざる（`未解決 + 解決済みが混在` ⇄ `…の混在` を実際に見つけた）|
| `IT実施フラグ` の付け方 | 手順 2 は仮置き |

## 次にやること

- ケースの実施は PD / QA の運用に乗る。AI に実施させるなら `e2e-prepare` → `e2e-execute`
- ケース PR を直したら、**`個別手順` のケースIDを軸にシート側を追随させる**
