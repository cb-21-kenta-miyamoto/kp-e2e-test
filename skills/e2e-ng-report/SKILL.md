# e2e-ng-report

## 概要

**テストが落ちた ≠ プロダクトが壊れている。**

切り分けずに起票すると、spec のロケータが壊れただけで issue を量産することになる。
とくに `※実装読み` だった期待値が多い改修では、③ が実際に起きる。

## いつ使うか

- `e2e-execute` でケースが落ちたとき
- 探索中にケースと無関係な不具合を見つけたとき

## まず切り分ける

| # | 何が間違っているか | 見分け方 | 行き先 |
| --- | --- | --- | --- |
| ① | **プロダクトの不具合** | 手で同じ操作をしても同じ結果になる。設計書の期待値と食い違う | GitHub issue を起票 |
| ② | **テストケース or spec の誤り** | 手でやると期待どおり動く。ロケータ / 前提データ / 待ちが原因 | ケースか spec を直して再実施 |
| ③ | **期待値が仕様として未確定** | 設計書にその挙動の記述が無い（`※実装読み` だった）| 設計書へフィードバック → 人間が判断 |

> [!IMPORTANT]
> **並列実行しているときは ② を先に疑う。**
> 別のサブエージェントが同じデータを触って落ちた失敗は、**プロダクトの不具合に見える。**
> 単独で流し直して再現するかを確かめる。

② と ③ は **issue を起票しない。** ケース / spec / 設計書を直して再実施へ戻す。

## ① のとき — issue を書く

### 構成（kpiee の既存 NG issue に揃える）

```markdown
## 事象
1〜3 行で症状。何ができないのか

## 再現方法
1. …（URL・対象・入力値まで書く。実際に操作できる粒度）
2. …

対比: 〜では成功する（何が違うと成功するのかを添える）

## 再現キャプチャ/動画
Drive の共有リンク

## 期待する結果
ケースの期待値をそのまま。設計書の該当節を引用する

## 解消方針
原因のファイル:行と、直し方の方向。**分かる範囲で書く**

## 補足情報
- 検出: どの PR / どのケースの実施で見つけたか
- 再現環境: ブランチ / commit / 環境
- 確認していないこと（**正直に書く**）
```

- ラベルは `bug` + 機能のラベル
- **原因まで追える場合は追う。** `解消方針` に該当箇所を書けると改修が速い
- **確認していないことを書く。**「比較表では未確認」のような限界を隠さない

### 起票したら

1. 実施記録の `NG Issue` 列にリンクを貼る
2. **ケース側に漏れがなかったかを考える。** ケース外で見つけた NG は
   「そのNGを踏むケースがテスト観点表に無かった」ということ。ケースを足すか判断する

> [!IMPORTANT]
> **issue の起票は人間の承認を挟む。** 案を作って提示し、OK をもらってから `gh issue create` する。
> スプレッドシートへの書き込みは承認不要だが、issue は別。

## ケースに紐づかない NG

探索中や別作業で見つけたものは **「ケース外のNG」タブ**へ 1 行足す。

ケースに紐づく NG は「ケース一覧・実施記録」タブの行そのものが記録になる
（合否 = NG + NG Issue のリンク）。詳細は issue に書くので、シートに再掲しない。

**「ケース外のNG」タブに 1 行増えたら、ケースを足すかを必ず判断する。**
