# e2e-case-review

## 概要

数百件のケースを**全部読まずに漏れを見つける**ためのスキル。

**「観点 → パターン → ケース一覧 → 被覆表」の 4 つが整合していれば、
ケース詳細は正しく展開されているとみなす。** 被覆表に「なし」の行が出ていないことがその根拠。

書式は [`references/case-format.md`](../../references/case-format.md)。

## いつ使うか

- `e2e-case-create` でケースができて、実施に入る前
- 他の人が作ったケース PR をレビューするとき

## レビューの 5 段階

| 段階 | 対象 | 回数 | 何を判断するか |
| --- | --- | --- | --- |
| 1. 全体設計 | `index.md` | 1 | レイヤーの割り方 / ブロックの分け方 / 担保の振り分け |
| 2. ブロック | 各ブロックの **1〜4 章** | ブロック数 | 対象範囲 / 観点の粒度 / 観点×パターンがケースになっているか |
| 3. 横断観点 | 既存チェックリスト 6 項目 | 1 | ブロックを跨いだ抜け |
| 4. 関連機能 | 既存の回帰マトリクス | 1 | 触っていない既存機能への影響 |
| 5. 抜き取り | 5 章（ケース詳細）| — | 手順・期待値の書き方 |

### 段階 2 で見ること

観点の切り方は kpiee-designs の
[`docs/onboarding/test-case-format.md`](https://github.com/f-scratch/kpiee-designs/blob/main/docs/onboarding/test-case-format.md)
が正本。そこの「4. 確認観点の書き方」「5. 切り方」「6. やらないこと」がそのままレビュー観点になる。

- 観点が**技術層**（API / DB / worker）で切られていないか
- 「〜が正しく動作すること」のような**述語形**になっていないか
- **最終結果として観測できる画面表示・状態**になっているか
- 設定項目ごとに割りすぎていないか（厚みは観点ではなくパターンで持つ）
- パターンが **1 レコード 1 値**か。抽象分類で済ませていないか
- **被覆表に「なし」の行が無いか**

### 段階 3 の横断観点（既存の正本を使う。自作しない）

ミドルバックテストのブックにある **「テストケースチェック観点」** の 6 項目。
各項目に `対応要否` と `理由/対応内容（どのケースに入っているか）` を埋める。
**「不要の場合でも、なぜ不要なのかを記載する」**のが決まり。

| # | 観点 | 見るところ |
| --- | --- | --- |
| 1 | パフォーマンス | 性能要件 / 既存からの劣化 / 本番のデータ量 |
| 2 | 権限 | アプリ権限・個別権限 / 管理者と非管理者 / **オプションアプリ未契約** / **API 直アクセス** |
| 3 | rakeタスク | 実行結果 / 切り戻し / **冪等性** |
| 4 | リリース手順 | スキーマ変更・キュー変更の順序 |
| 5 | モバイル互換性 | モバイル API に改修が入るか |
| 6 | 確認デバイス | **キーバインドを自前制御している / wysiwyg を使っている**なら OS 観点（Windows/Mac）|

> [!TIP]
> **6 は見落としやすい。** `contenteditable` + `metaKey/ctrlKey` の分岐 + `isComposing`（IME）を
> 使っているコンポーネントがあれば該当する。OS 観点と日本語変換中の Enter を確認するケースが要る。

### 段階 5 の抜き取り規則

全部読まない代わりに、読む対象を規則で決める。

| 対象 | なぜ読むか |
| --- | --- |
| **`※実装読み` / `※未確定` が付いたケース — 全件必読** | 設計書に根拠が無く実装から読んだ期待値。読まずに承認すると「実装に合わせたテスト」を通すことになる |
| 各ブロックの A 群の先頭 1 件 | 書き方の基準がブロック間で揃っているか |
| P0 のケース | 優先度を振ってから |

## 承認

- レビューコメントはケース PR の **inline review**（ケース一覧の行に付けられる）
- 承認の記録は **「設計/ケースレビュー承認管理シート」**（PR テンプレートの必須項目）
- **完了の条件は `※実装読み` が 0 件になること。** 確定できないものは設計書へフィードバックする

## 順番についての注意

本来は **段階 1〜2 を通してからケース詳細を展開する**のが手戻りが少ない。
ケースを全部書いてからレビューに出すと、観点の切り方に指摘が入ったとき
ケース詳細まで書き直しになる。
