# e2e-case-create

## 概要

改修に対して **E2E で確認すべきことを全部書き出す**スキル。

出すのは「観点とパターン」で止めたものではなく、**1 ケースを単体で実施できる粒度まで展開したもの**。
AI に実施させるには、掛け合わせの解決・具体値・前提データが実行者の暗黙知になっていては動かない。

書式は [`references/case-format.md`](../../references/case-format.md) が正本。**先に読む。**

大元の方針は [dx-kpiee#18521](https://github.com/f-scratch/dx-kpiee/issues/18521)。

## いつ使うか

- 設計書 PR ができて、テストの設計に入るとき
- 実装 PR の動作確認を体系的にやりたいとき

## 手順

### 1. 材料を集める

**設計書だけではミドルバックのケースが書けない。** 次を全部読む。

| 材料 | どこ | 何が取れるか |
| --- | --- | --- |
| 基本設計書 | kpiee-designs の PR ブランチ | 機能概要 / 対象範囲 / 制約 / 権限 / 対象外 |
| 詳細設計書 | 同上 | **「異常系と境界条件」「テスト観点」の節が最良の材料** |
| API 設計 | 同上 `api/*.md` | 入力検証・エラーコード・業務ルール |
| 実装 | dx-kpiee の feature ブランチ | 設計書に無い挙動、i18n の文言、DOM の手がかり |
| Notion 仕様書 | `連携可能 = ⚪︎` のページだけ | 確定仕様 |
| 既存の NG issue | dx-kpiee | **ケースの漏れが見つかる**（後述）|

> [!IMPORTANT]
> **設計書が `main` に無いことがある。** PR のブランチを fetch して読む。
> 設計書とコードが食い違っていたら**コードを正とし、食い違いを記録する**。

### 2. ブロックに割る

4 レイヤー × 機能のまとまりで割る。1 ブロック = 1 ファイル = 実施の単位。

- `SPEC-*` は**画面単位**で割る（詳細画面 / 一覧 / ダッシュボード …）
- `NFR-*` は**非機能の種類**で割る（性能 / 上限 / 整合性 / エラー / 移行 / 非影響 / 表示）
- `SCN-1` は 1 ファイル
- `MB-*` は **API の責務**で割る（CRUD / 取得 / 認可 / 複製）

### 3. ブロックごとに 観点 → パターン → ケース の順に書く

**この順番を崩さない。** 観点があってケースが決まる。

1. `1. 対象範囲` — 対象と対象外。対象外は他ブロックへリンクする
2. `2. 観点サマリー` — 確認観点詳細（何を確認するか）と パターン観点詳細（**組み合わせ前の全量**）
3. `3. ケース一覧` — ケース群とケースIDを件数つきで
4. `4. ケース` — 1 ケースずつ。パターン詳細 / 操作 / 期待値
5. `5. 被覆表` — どのパターンが 1 ケースも使われていないか

### 4. 期待値が決まらないものに印を付ける

| 印 | いつ |
| --- | --- |
| `※実装読み` | 設計書に記述が無く、実装を読んで書いた |
| `※未確定` | 期待値そのものが決まっていない |

**印を付けずに断定しない。** ここを曖昧にすると「実装に合わせたテスト」になる。

### 5. 既存の NG issue と突き合わせる

**ケースの漏れはここで見つかる。**

```bash
gh issue list --repo f-scratch/dx-kpiee --search "<改修ID>" --state all --label bug
```

過去の NG が既存ケースのどれにも当たらないなら、**そのパターン観点が無い**ということ。
実例: #18520（値のないセルで投稿失敗）から「セルの値」のパターン観点が
無いことが判明し、ケースを 2 件追加した。

### 6. PR を出す

- 置き場所は kpiee-designs の `docs/feature/<領域>/<改修ID>/test/`
- **`docs/.vitepress/config.mts` のサイドバーに登録する**（手動。自動生成ではない）
- `yarn docs:build` を通す（PR テンプレートのチェック項目）
- **設計書 PR とは別 PR** にする
- **ドラフトで出す。** レビューの結論が出るまで確定させない

## やらないこと

- **観点とパターンだけで止めない。** ケースまで展開する
- **設計書に無い期待値を断定しない。** 印を付けて残す
- **リンクを貼る前に開かずに済ませない。** `gh api repos/.../contents/<path>?ref=<branch>` で 200 を確認する
- **独自の記号・略語を初出で展開せずに使わない**

## 次にやること

[`e2e-case-review`](../e2e-case-review/SKILL.md) でレビューして承認まで持っていく。
